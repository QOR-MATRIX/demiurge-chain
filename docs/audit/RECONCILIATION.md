## 3. Contradictions, ranked by blast radius

**Contradictions** are places where the code contradicts the direction, or where two stated goals
cannot both hold as written. The most damaging come first.

**Blast radius** means what fails and for whom:
- **Critical:** money or keys.
- **High:** identity, the base layer, or the first release.
- **Medium:** honesty of interfaces, and tensions in the economic model.
- **Low:** language, documentation and styling.

### 3.1 Critical

**1. Any account holder can create CGT on the running chain.**
- **Stated:** supply changes only through designed issuance, and no path creates CGT outside `--dev`
  (`AGENTS.md` §5).
- **Actual:** a signed `ModuleCall` to `Balances` with `Transfer{from: caller, to: caller, amount}`
  passes the only check, `from == caller` (`framework/core/src/runtime.rs:404-408`). The transfer then
  reads both balances before writing either, so the second write sets the caller's balance to
  X + amount (`framework/modules/balances/src/balances.rs:85-104`). **V.**
- **Why it matters:** every validator executes it identically, so the chain does not fork. It inflates
  silently, and `Balances:TotalSupply` stops matching the sum of balances. The `Transfer` transaction
  type guards against self-transfer (`transaction.rs:95-97`); the module call does not.

**2. The QOR ID admin account can be taken over by anyone who reads the repository.**
- Migration `services/qor-auth/migrations/008_seed_godmode.sql` is tracked in git. It seeds user
  `godmode` with role `god` and backup code `GODMODE-RECOVERY-2026` (`:44, 52, 59`). **V.**
- The public route `/api/v1/auth/reset-password-backup` (`src/main.rs:163`) compares that code
  (`src/handlers/auth.rs:466`) and sets a new password. **V** (route and comparison), **S** (the rest of
  the flow).
- A god-role token opens every admin route. On any database where migration 008 ran, the account is
  compromised. Whether it ran on a live database is **Unknown**.

**3. Token-signing secrets and database credentials are committed.**
- `services/qor-auth/config/production.toml` is tracked in git. It sets the access and refresh token
  secrets, the database URL and the Redis URL. **V** (tracked, and the fields have values; the values
  were redacted when read and not judged).
- The sweep reports they pass the service's own validation and load when `RUN_ENV=production`
  (`src/config.rs:84, 117-143`). **S.**
- Anyone with the secret can mint a token with any role. If these values were ever deployed, they are
  exposed.

**4. The server generates, stores and hands out agent private keys.**
- **Stated:** QOR ID mints scoped, revocable keys, and the agent never holds the user's identity
  (ADR-010).
- **Actual:** `services/qor-auth/src/handlers/agents.rs:98-147` draws 32 random bytes, stores their hex
  as the agent's *public* key, hashes them as its password, and returns them in the response. **V.**
- The agent endpoints are also missing checks. Registration ignores the caller and sets no controller
  (`:105-107`). Listing returns every agent, and capability updates and deletion check no ownership
  (`:199-287`). **S.**
- The frozen `packages/agent-foundry/src/agent.ts:509-542, 627-629, 695` also returns raw private keys,
  and puts one in a URL query. **S.**

**5. The launcher lets the phrase out, while the direction says "unexportable vault".**
- `vault_export_phrase` is a registered IPC command (`tools/qor-launcher/src-tauri/src/lib.rs:189, 507`)
  that returns the 24-word phrase to the webview, given the passphrase (`vault/mod.rs:255`). **V.**
- The phrase also reaches the webview at generation (`lib.rs:151-154`). **S.**
- Private keys have no export path. **S.**
- The webview can repoint the RPC and auth endpoints (`lib.rs:371-387`). The vault signs QOR ID
  challenges as raw bytes with no domain tag (`identity/mod.rs:140, 169, 193`). **S.**
- Whether phrase export (a normal backup feature) is allowed under "unexportable" is the owner's call.
  The direction and the code disagree as written.

### 3.2 High

**6. "Built on a purpose-built Substrate L1" versus a custom chain.**
- The chain has no Substrate dependency (`framework/Cargo.toml:3-84`; `framework/core/src/lib.rs:3`). **V.**
- ADR-013 settles the direction. The consequence is that every base-layer line written for M1 is
  retired, and no Polkadot SDK code exists yet. The only Substrate code, `aeons/` and
  `packages/blockchain-wasm`, is built by no workspace. **V.**

**7. DRC-369 is not the "living object" the direction describes.**
- **None of the seven claimed capabilities is fully implemented** (§4.1).
- **Unauthorised mint:** mint writes any owner the caller names (`drc369/src/nft.rs:389-444`). **V.**
- **Unchecked nesting:** nest checks the child's owner but not the parent's, and allows cycles
  (`nft.rs:745-785`). Burn is refused while children exist, so a stranger can block an owner's burn.
  **V** (checks), **I** (griefing).
- **No CGT moves:** nothing in the crate moves CGT (`royalty_distributor.rs:267-269`). **S.**

**8. "SDKs ship alongside" versus no SDK that works.**
- No package in `sdk/` or `packages/`, and neither the Unreal SDK nor the hub, builds a transaction the
  node accepts. The causes are the wrong payload, Sr25519 signatures, unregistered method names, and
  REST calls to a JSON-RPC node (§4.1, sweep table). **S.**
- Combined with the unknown publication status (§2.2), the ecosystem may already see
  `@demiurge/sdk@1.0.0` that cannot transact.

**9. "Fee sponsorship so end users transact without holding tokens" versus what either chain allows.**
- **On the current chain:**
  - `sponsor_transaction(developer, _user)` spends the developer's energy and ignores the user
    (`framework/modules/energy/src/energy.rs:136-155`). **S.**
  - Every sender still pays energy (`runtime.rs:330-334`). **S.**
  - Users transact without tokens today only because a new key regenerates energy from block 0
    (`energy.rs:115-130`). That is a free Sybil allowance, not sponsorship. **S.**
- **On the Polkadot SDK:** standard `CheckNonce` refuses a sender with no providers and no sufficients
  (inventory F-Q1, verified in SDK source). "Transact without holding tokens" therefore needs a
  deliberate account-existence design. Storage deposits for minting make it harder still (inventory
  F-D7).
- **The tension:** the goal cannot hold alongside spam resistance and standard account rules without a
  design that does not exist yet (inventory Q-12).

**10. "Session keys and scoped delegation" versus nothing enforced.**
- Session keys store only an expiry. The transaction format has no signer and origin split, so a
  session key authorises nothing (`framework/modules/session-keys/src/session.rs:211-218`;
  `transaction.rs:43-65`). **S.**
- `framework/modules/qor-identity` is not dispatched at all. **S.**
- `qor-auth` issues JWT scopes that no handler checks (`src/models/session.rs:79-85`). **S.**
- Logout and session revocation are no-ops (`src/handlers/auth.rs:330-336`, `profile.rs:186-193`). **S.**

**11. "On-chain governance" versus a module nothing uses.**
- `framework/modules/governance` has no dependents.
- Voting power is a caller-supplied number under an `f64` square root.
- "Execute" returns encoded bytes and applies nothing (`governance/src/lib.rs:97-304`). **S.**
- Separately, holding-weighted voting sits against ADR-002's spend principle (U-10). Both cannot be
  maximised at once.

### 3.3 Medium

**12. The API reports finality that does not exist.**
- `chain_getHealth` returns `finality: 2000` (`framework/rpc/src/methods.rs:345`). **V.**

**13. "Burn offsets issuance so net supply trends flat" versus near-zero, often sponsored fees.**
- Burn is a share of fees. The direction also wants fees near zero and often sponsored. At low and
  moderate volume, burn is therefore small against a fixed-percentage issuance, and net supply grows
  (I).
- "Roughly flat" holds only above a transaction volume nobody has modelled (the inputs to OPEN-1 and
  OPEN-4).
- This is a tension to model, not a defect. Documents must not present flat supply as the expected
  outcome until the model exists.

**14. "Creators price in a stable display unit" versus "no peg".**
- Converting a stable display price to CGT at settlement needs a reference rate (U-2).
- A unit that stays stable while CGT moves is stable *against something*. If that something is a

- If it is not, what it is stable against is **Unknown**.
- The direction's two sentences cannot both be taken at face value until U-2 and U-3 are answered.

**15. "Staking for distribution" as a demand sink.**
- If staked CGT is locked and returned, the sink creates demand to hold, not to spend (U-7). ADR-002

**16. The launcher mishandles amounts.**

**17. Deployable-looking operational files do not work.**

- `config/production/demiurge-node.service` runs a validator from a genesis the node refuses. **S.**

**18. QOR ID's wallet link contradicts itself.**
- The database accepts only `^0x[0-9a-f]{64}$` (`migrations/009_fix_on_chain_address.sql:49`). **V.**
- `link_wallet` requires a 32 to 48 character "SS58" string, performs no signature check, and updates

## 8. CGT handling, 19 October 2026

A second read-only audit, of how the active scope handles CGT, taken on 19 October 2026 at the owner's direction that
CGT be developed to the standard of a currency and that compliance is a must. It measured the code against AGENTS.md
§5 and §6 and ADR-101. Unlike §1 to §7, this section is current.

**Sound:**
- Every amount is integer embers in `u128`.
- Every ratio uses the SDK's helpers (`Permill::mul_floor`, `multiply_by_rational_with_rounding`, the Mesh's
  `serving_cost`).
- No pallet creates CGT.
- Amounts cross JSON as decimal strings: no `Serialize` struct in the active Rust code carries a `u128`.
- Every open value in code is marked as a placeholder.
- Transactions carry a chain binding, an expiry and a nonce.
- An ARQ Wallet outcome is paid once.
- A buyer's `max_price` and `buy_exact` hold the seller to what was shown.
- ARQADE keeps no balances off chain.

**Fixed the same day (branch `session/cgt-compliance`):**

| Finding | Fix |
| --- | --- |
| QOR ID's schema still held migration 005's donation scheme: a trigger setting a "staking rewards" bonus of 2% to 10% and a fee discount of up to 10% by fiat tier, and columns of CGT "distributed" for dollars. Invented values for open questions, in the language §6 rules out. Nothing read it | Migration 024 drops the trigger, its functions and the perk columns, and moves the three tables whole to a schema `retired`, so no record of a payment is lost. Tested against Postgres from the state before it |
| An agent's spending limit accepted a negative number, and no document said it is not enforced | Refused by the service and by the table (migration 025). The column says it is a whole number of CGT, recorded and not enforced (Q-9), until `pallet-agent-caps` (M5.2) enforces caps in embers |

It also took a sign: "1.+5" read as 1.05 | A separator is read only between groups of three digits in the whole part. Anything else, a sign included, is refused with a message naming the rule. The core's `format_sparks` takes digits only |

Its intro said "you may lose more than you could win" | P7.23's removal: no Energy, entry cost, draw or token wallet. Play is free, and the intro and notice say nothing is bought, staked, won or lost |
| ARQADE's tip panel passed a whole number of CGT through a JavaScript `Number` | `BigInt` |
| The launcher said a starter grant is the usual first step, and the homepage that test CGT comes from a faucet. Neither exists | Both say test CGT is sent to testers by hand |
| The language rule was enforced only on the homepage, by a check CI never ran | CI runs that check, and a check over the active scope's user-facing copy (GATES change log) |

**Open, engineering:**
- **Marking a welcome grant paid (M).** It accepts any well-formed hash, without checking the chain for the sender,
  the recipient or the amount, and one transfer can settle several grants. It should verify on the finalised chain,
  and a later migration should make the hash unique, once production is known to hold no duplicates.
- **ARQ Wallet bookkeeping (S, needs a runtime upgrade).** `owed` and `Held` use `saturating_sub` where the module
  promises no amount is saturated. The royalties pallet's `unwrap_or(0)` would pay a recipient nothing rather than
  fail. Both should refuse.
- **`qor://pay` (M).** The guard against paying one request twice is a file on one device. Before signing, the
  launcher should look for the request's remark on the finalised chain.
- **The Mesh's amount form (S).** It parses amounts on its own, takes no Sparks and has no ceiling. It should use the
  core's `parse_amount` (L11.1).

**Open, the owner's and a lawyer's** (§4.0 of HANDOFF lists them with who unblocks each):
- **Terms of Service and a privacy policy.** QOR ID, Social and ARQADE are live and hold emails, messages and sessions,
  and none of the active scope has either.
- **Deleting and exporting an account.** No route does either for a person, only an admin ban.
- **Rewards, prizes and chance.** Whether ARQ Wallet prize rounds, ADR-102's Spark rewards for play, backing and the
  welcome grant are lawful, where, and under which rules (U-15 to U-18).
- **Identity and access duties.** Which KYC, AML, sanctions screening, geofencing and age gating apply.
- **A public statement** that devnet balances never carry into any network with value.
- **Fees and spam** (OPEN-4, U-4), and which transaction records must be kept, which shapes the indexer (M5.4).
